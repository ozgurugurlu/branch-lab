# Agent execution and capabilities

The application uses real Mastra agents and `createTool` tools. A live turn starts with a required scoped read, may request one additional read or web search, and ends with a typed proposal. Three model steps and two tool executions are the hard maximum per agent. Tool execution is sequential within an agent; up to three actors run concurrently against the same frozen prior-round state. SDK retries and workflow step retries are disabled. A retry initiated by the user can still repeat provider charges after an interrupted operation.

## Personas and capabilities

A persona is a fictional actor's name, role, description, goal, modeled stance/influence, source assignments and memory. The live architect generates these fields from the scenario and actor-visible material and is instructed to create fictional composites with distinct incentives. These are modeling assumptions, not verified biographies, surveyed opinions or calibrated psychological traits. Shape/reference validation does not prove that a persona is realistic.

The demo instead selects a fixed urban, product, technology or community catalog by English scenario keywords and uses English templates. It accepts user text but does not translate it. Names can recur with different roles across catalogs: Maya Chen is an employee representative in the technology catalog and a neighborhood organizer in the urban catalog. Seeded values and fixed rules determine demo variation; no LLM invents these personas or semantically interprets imported evidence. The requested population takes catalog entries in order, repeating archetypes with numbered names above eight actors.

A fictional role is separate from its capability profile. New worlds retain an explicit profile; if the architect omits it, code infers one from role/goal text with a stable actor-number fallback. The four profiles below select tools, not additional authority over another actor's data.

Prompt protocol `2026-10-01.1` asks the architect to preserve explicit counterfactual premises: if everyone owns a robot, ownership remains universal while maintenance, capabilities or service quality may differ as stated assumptions. Actor prompts ask for concrete incentives and constraints without mandatory opposition, consensus or unsupported stance changes. Worlds, actor actions and reports use the dominant language of the original scenario question; chat and interviews use the current question's language. Reports address the question's substantive parts and distinguish recorded observations from causal hypotheses, assumptions, tradeoffs and possible next tests. These are generation instructions; validation enforces structure and accessible references, not behavioral realism or forecasting accuracy.

| Agent or profile    | Available tools                                                                                  | Information boundary                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Architect           | `inspect_world_constraints`, `read_actor_sources`                                                | Actor-visible documents only; never analyst-only sources                      |
| Community liaison   | `inspect_neighbor_events`, `recall_own_memory`, `inspect_contacts`                               | Own memory, direct contacts and their visible prior events                    |
| Evidence researcher | `read_assigned_evidence`, `recall_own_memory`, `compare_observed_stances`; optional `search_web` | Assigned documents and observed public stances                                |
| Operations planner  | `inspect_interventions`, `read_assigned_evidence`, `recall_own_memory`                           | Applied interventions, assigned documents, own memory                         |
| Policy reviewer     | `inspect_contacts`, `inspect_interventions`, `recall_own_memory`                                 | Direct contacts, applied interventions, own memory                            |
| Analyst             | `inspect_metrics`, `query_events`, `read_all_evidence`                                           | Computed metrics, latest four rounds / 48 public events, all imported sources |

Actor interviews retain the actor's capabilities and information boundary. Profiles are explicit fields on new actors; the fallback for older worlds infers a profile from the fictional role and goal, then the stable actor number. This inference is a modeling assumption, not a verified property of real people. Actors with the same profile still receive separate tool closures with different own-memory, source and neighborhood permissions.

Tools return actual data from their injected, permitted snapshot. Actor tools never receive the full simulation or another actor's private memory. They cannot mutate state, execute code, select an arbitrary endpoint, read files, or access server credentials. Text results and imported documents remain untrusted model inputs. The prompt declares this boundary, while code enforces tool availability and the data that each tool can return. Tests establish these software boundaries; they do not prove that a language model will always resist every injected instruction.

Web search additionally requires a configured server provider and explicit per-run consent. Only research-profile actors receive this tool. Queries may contain scenario-derived information and are sent to the configured search service. Results are bounded snippets and links; the runtime never fetches a result URL. Search results are unverified outside evidence and do not create stored source IDs. Without consent, configuration, or a research profile, the search tool does not exist. Deterministic demo mode does not search the web.

Tools and structured outputs use Mastra's JSON prompt injection so the same bounded protocol works with cloud and OpenAI-compatible local models. The final object is always checked with Zod plus reference and range validation. A local model must support tool calls as well as JSON output; ignoring the required first tool fails with a capability error, without a demo fallback. Stored source IDs and accessible event IDs are checked after generation, including citation-shaped inline references.

Execution events record real phase starts, tool starts/results, durations, failures and model-step counts. Summaries are fixed application text; raw prompts, tool result bodies, model reasoning and private chain-of-thought are not stored in this feed. A completed model phase means a typed proposal was received; the enclosing operation must still validate and commit it. The deterministic demo executes the same scoped read functions and labels these events explicitly as demo work with zero model calls.

The creation manifest preserves the engine and prompt versions that created a run. Each new round records its execution versions independently, so older saved runs can continue after compatible upgrades. Persistence, lease fencing, checkpoints and the operation journal belong to the server layer, outside the ephemeral Mastra workflow.

## Reports at the end of a run

When a user-started browser run reaches its configured round limit, including through a manual final step, the browser awaits a separate report request after the final round is saved. Pausing auto-run or losing connectivity before that request leaves reporting as an explicit action. The analyst returns a direct answer to the original scenario question, followed by recorded-event findings, metrics and uncertainties. This is a conditional interpretation of the simulated world, not a forecast guarantee. Report failure leaves the completed rounds intact and offers an inline retry. Reloading a tab with retained auto-run intent reconciles the exact operation and continues the work already requested; opening an existing run without that intent starts no inference. A run's `completed` status describes its rounds, not whether reporting succeeded.

Automatic and manual reports use the same analyst tools, evidence window, source limits and existing model consent. Analyst-only sources remain available to the analyst and excluded from actor inputs. Reporting introduces no web-search capability for the analyst. Existing saved reports are reused; older reports without a separate direct-answer field offer an explicit **Update report** action. Live regeneration can incur model charges.

After validating a generated report and its citations, the server attaches English `contextNotes` as separate evidence-coverage metadata. The interface displays them under **Evidence coverage**, outside model-written uncertainties and narrative. Analyst chat has an English **Analyst context** disclosure for its four-round / 48-event window and bounded source excerpts. Live chat receives context/history limits in its payload and is instructed to explain material limits in the current question's language; the engine appends only bare citation IDs, without English evidence or context-limit footers.
